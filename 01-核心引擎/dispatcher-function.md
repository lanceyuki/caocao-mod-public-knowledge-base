# 特技调度函数：追踪预检与分支

> **适用范围**：调度结构、查表规则和地址都可能随引擎构建变化。本文给出一个分析样本中的控制流和可复用的核对方法；不要把样本中的表项、编号或地址直接用于其他目标。

## 调度函数做什么

调度函数位于桩函数和后续处理逻辑之间。它可能从参数或寄存器取得一个选择值，运行预检，再根据预检结果调用处理函数或直接返回。仅凭函数名、连续地址或某个寄存器值，不能判断它查询的字段和返回值含义。

## 一个样本中的控制流

下列伪代码概括了样本中观察到的一类分支。它省略了栈帧和寄存器保存指令；`<table_key>` 与 `<lookup>` 表示需在目标文件中重新定位的值和函数。

```text
set <table_key>
result = <lookup>(context, <table_key>)
if result != 0:
    return
call <core_handler>(original_arguments)
```

在该样本中，预检结果非零时会跳过核心调用，结果为零时继续调用。这个分支方向是静态控制流证据；它本身不能证明零或非零分别表示“拥有特技”“查表命中”或“查表失败”。

样本里可作为定位线索的地址包括预检包装函数入口 `0x9BBFE4`、核心处理入口 `0x4101D9` 和上层包装入口 `0x42518F`。`0x9BBFE4` 在该样本中是可执行代码，不是数据表地址；此处只说明调用位置，不据此推定其返回值或内部检查的通用语义。这些地址不能视为跨构建稳定接口。

## 还原目标引擎的调度逻辑

1. 从桩函数的交叉引用找到调度函数候选，并确认函数边界。
2. 记录调用预检前设置的参数和寄存器，特别是 `ECX`、`EDX` 与栈参数。
3. 跟进预检函数，核对它实际读取的数据和所有返回路径。
4. 回到调度函数，逐一记录比较指令、条件跳转和每条分支的目标。
5. 跟进核心处理函数，并检查原始调用者如何消费结果。
6. 把静态分支证据与运行时观察分开记录；声称游戏效果时补充目标引擎和数据配置下的验证。

## 不要从局部模板推断的事项

- 不要把一个样本中的表项步长、选择值或特技编号当作固定分配规则。
- 不要仅凭 `test eax, eax` 推断零值代表“命中”或“未命中”。
- 不要假定直接调用核心处理函数与经调度函数调用具有相同前置条件和返回值语义。
- 不要把地址清单、可用位置或项目补丁映射当作公共引擎知识。
