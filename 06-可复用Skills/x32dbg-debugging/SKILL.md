# x32dbg/x64dbg 动态调试

## 用途与边界

本 skill 讲解如何用 x32dbg/x64dbg 获取可复核的运行时证据。它聚焦调试器操作和观察记录；机制解释、补丁设计与代码审查仍需相应的静态分析和开发流程。

这里只描述通用调试方法，不提供目标专属地址、数据结构偏移、代码洞、补丁编号或本地环境配置。若由脚本或其他适配器控制调试器，先查该适配器自己的工具说明；不能把适配器的行为直接当成 x32dbg/x64dbg 本身的行为。

## 开始前

1. 选与目标进程架构匹配的调试器。x64dbg 文档说明，调试器与目标架构需匹配；例如 x32dbg 不能附加到 64 位进程。
2. 决定从程序启动还是附加到现有进程。附加前记录进程身份、主模块和复现步骤；若当前已有调试目标，先确认切换目标会怎样影响它。
3. 先明确要证明的具体事件和结果。把触发输入、预期执行点、应观察的寄存器/内存/画面结果写成简短检查项。
4. 对照当前目标的模块和反汇编定位断点。若地址来自另一个进程、重启或旧构建，先确认模块基址，并用模块相对偏移（RVA）核对实际地址；不要把旧绝对地址直接当作当前地址。

## 选择观察方式

| 目标 | 合适方式 | 需要留意 |
|---|---|---|
| 确认执行经过一条指令 | 软件执行断点 | 断点必须落在目标事件真正执行的位置；高频位置应使用条件或记录方式，避免频繁暂停。 |
| 观察少数地址的读写或执行 | 硬件断点 | 数量和对齐受处理器及调试器限制；先确认当前设置是否成功。 |
| 找出某个内存区域的访问 | 内存断点 | 监视范围可能覆盖整个内存区域并触发很多次；先缩小区域或增加筛选条件。 |
| 观察模块加载、异常或特定线程 | 对应事件断点 | 先确认事件定义和异常传递方式，避免把被调试程序原本处理的异常误判为故障。 |
| 地址固定，但只在条件满足时暂停 | 条件断点 | 条件只会在该断点实际命中时求值；表达式错误可能导致意外暂停。先用少量命中验证条件。 |
| 不知道条件在哪条指令首次成立 | 条件跟踪 | 跟踪可能产生大量记录并明显拖慢程序；限制范围、线程和记录长度。 |
| 只需统计或采样，不应暂停程序 | 命中计数或日志断点 | 记录必要字段，避免在高频路径输出过量日志。 |

x64dbg 原生软件条件断点在断点命中时会无条件递增命中计数，然后求值 break condition；默认条件为 1，任何非零值都会暂停，0 则继续执行。因此，适配器显示命中次数增加本身不能说明条件已经成立或调试器已暂停。未暂停时，分别检查断点状态、条件表达式和进制、实际暂停状态，以及适配器如何解释命中计数。官方文档也区分条件断点与条件跟踪：条件断点只能在其地址被执行时检查条件；如果条件可能在其他位置成立，应考虑条件跟踪。适配器和不同版本的界面行为需按各自说明核实。

## 命中后的取证顺序

每次暂停后按以下顺序核对，避免把“断点亮了”误写为机制已经验证：

1. 确认进程、模块、线程和当前地址；记录模块基址与 RVA。
2. 查看当前指令及前后控制流，确认执行停在预想分支，而不是相邻的准备、派发或清理阶段。
3. 记录相关寄存器、标志位、调用栈和必要的内存范围。读取指针前先确认它位于有效、可读区域；不要只凭一个瞬时数值命名字段语义。
4. 对比命中前后的状态，追踪关键值的写入者、后续修饰和实际消费者。只观察到读取或函数返回，不等于已证明最终效果。
5. 若需要继续游戏或程序，先完成当前断点的采样，再恢复执行。一次只列出需要用户触发的步骤和回报内容；不要在动作已自动完成后再把此前的断点命中当成结果验收。

### 单步操作

- **Step Into** 用于进入当前调用并检查被调函数；**Step Over** 用于越过当前调用；**Step Out** 用于运行到当前函数返回附近。
- 用“运行到选中地址”前先确认目标地址仍属于当前模块和预期代码路径。目标路径未命中时，程序可能继续运行，因此要准备明确的停止条件。
- 不要为了看完整机制而逐条单步穿过无关的大段代码。先用静态调用关系缩小观察窗口，再围绕关键分支和消费者单步。

### 表达式与条件

- 在 x64dbg 表达式中，数字默认按十六进制解释；使用条件表达式前确认数字进制、指针宽度和字符串编码。
- 先用表达式计算器或短暂停点验证条件，再把条件挂到高频断点。
- 条件断点只会在其地址被执行时评估。不要把“条件尚未成立”与“断点从未命中”混为一谈；分别核对命中计数和条件结果。

## 运行时内存写入

内存写入会立刻改变被调程序状态，可能污染后续观察。只有在目标、地址、长度和预期值都明确且可恢复时才用于短期实验：

1. 暂停目标并记录原始字节、模块/RVA、保护属性和当前线程状态。
2. 只写已确认的最小字节范围；不要把未知数据区域当作空闲空间。
3. 立即读回并逐字节比对；若不符，停止并恢复原始值。
4. 记录实验后的状态，并在结束前恢复原字节或重启到干净基线。
5. 运行时写入只证明当前进程中的临时状态；它不证明磁盘文件已改变，也不等于持久补丁已经验收。

## 证据记录

每次动态观察至少保存：

- 目标进程和模块身份，以及调试器架构；
- 断点的模块/RVA、类型、条件和命中次数；
- 触发步骤、线程、停点指令、寄存器、调用栈和关键内存读回；
- 观察到的分支、后续消费者和画面/业务结果；
- 证据层级：静态定位、运行时命中、内存读回、受控路径结果、最终界面或玩法验收；
- 未覆盖的路径、异常和复测条件。

“断点命中”只证明执行到该位置。“内存读回符合预期”只证明读到该瞬时值。只有观察到契约要求的最终消费者和外部结果，才能把结论提升到对应验收层级。

## 常见误区

| 误区 | 修正方法 |
|---|---|
| 把旧构建的绝对地址直接用于当前进程 | 核对当前模块基址、RVA、字节和指令边界。 |
| 在触发动作刚发出时设断点，却把命中当成最终选择或结算 | 把断点放到实际选择/写入/消费位置，逐阶段记录并在继续执行前采样。 |
| 条件断点计数增加，就以为条件表达式已经满足 | 查清调试器原生条件行为、适配器返回值、命中计数和暂停状态；不能用一层的表现推断另一层。 |
| 把一个寄存器值称为字段含义或最终结果 | 追字段的写入、变换、分支和消费；必要时对比成功/失败路径。 |
| 内存值正确但界面不对，就认定计算错误 | 同时检查值属于哪个对象、界面读取/刷新哪个对象，以及后续可见更新是否执行。 |
| 把运行时写入当成持久补丁 | 分开保存进程内读回、磁盘文件读回和重启后结果。 |
