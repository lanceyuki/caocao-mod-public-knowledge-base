# 经典战棋引擎功能开发与移植

## 概览

把功能说明转成可验证的行为契约，再以目标引擎为准追清数据和控制流，最后用可复现、可回滚的改动实现并分层验收。参考引擎、旧补丁、函数名和旧文档都只是线索；它们不能代替对当前目标的核对。

本 skill 面向经典战棋游戏及相近的 32 位二进制引擎。它适用于新增功能、修改现有机制、跨构建移植、故障修复和机制研究，不局限于特技移植。

## 何时使用

- 要新增或修改战斗、状态、属性、界面或其他引擎行为。
- 要把参考版本或旧补丁中的功能移植到另一份引擎。
- 要在写补丁前追清一个已有机制的判断链、数据链或最终效果。
- 补丁应用后出现启动失败、异常分支、崩溃或回归。
- 需要判断二进制补丁是否可行，以及怎样证明它有效。

仅编辑地图、美术、文本或普通应用程序代码，且不涉及二进制引擎行为时，使用相应的内容或代码工作流。

## 工作流程

### 1. 锁定目标并保护基线

1. 找到本次实际要运行和修改的目标文件；把参考文件、目标文件和候选补丁分开标记。
2. 阅读项目中的知识库、历史记录和本地开发约定，确认已有结论、未决事项、补丁依赖和已验证范围。
3. 保留未修改的目标副本和精确回滚材料。将目标版本指纹保存在本地审计材料中；公共说明不抄录内部哈希、路径或构建标识。
4. 若是在排查崩溃或异常，先保留失败状态并确认能否复现。不要先覆盖现场或假定最近的改动就是原因。
5. 对生成器、注入器、清理器等有写入或外部副作用的入口，先静态审查写集和路径检查；红灯测试使用 mock 或隔离副本，不直接执行可能改写目标的旧入口。

**出口：** 能明确说出目标文件、参考材料、当前基线和本次允许改变的行为。

### 2. 写出行为契约和验收场景

把特技说明、游戏文本、既有行为或需求整理成短契约。说明文本可作为独立语义线索，但要用目标代码流核实：

- 触发条件和执行时机是什么？
- 作用对象、数据来源、计算输入和预期输出是什么？
- 哪些门控、优先级、状态、装备或已有机制会改变结果？
- 哪些路径必须保持原样？哪些边界情况需要单独验收？

将每条内容标成**已确认、推断或待查**。为命中、未命中、边界值、原生门控和回归路径安排可观察的验收场景。不要把“能编译”或“补丁已应用”当作行为验收。

### 3. 以目标引擎为准追踪证据

1. 用参考引擎和旧补丁提出候选路径；逐项对照目标中的函数边界、调用目标、数据布局、分派逻辑、共享状态和门控条件。
2. 先明确当前问题要证明什么，再沿最短充分路径从输入或判定起点追到相关结果的最终消费者和副作用：读取 → 选择/计算 → 修饰 → 写入或返回 → 实际使用处。达到问题所需的消费点后停止；除非契约依赖，不要把相邻伤害、界面或状态流程扩成独立研究目标。缩小研究范围不等于跳过候选补丁可达的分支或契约要求的场景；按实际控制流核对适用的命中/未命中、早退、门控和回归分支。函数名称、参数注释或单次寄存器快照不能证明完整语义。
3. 对 x86 路径，核实调用约定、栈清理、寄存器与标志位存活、分支汇合点和返回路径。若反汇编可能经过内嵌数据失步，改用原始字节、已知边界或交叉引用核对，并抽查搜索覆盖范围。
4. 分开记录静态反汇编、运行时读回、受控启动和游戏内效果。动态断点应放在所需事件实际发生的位置；“断点命中”只证明执行到该点。
5. 记录每项结论的证据来源、适用目标和未覆盖边界。跨版本相似不等于已证明等价。

**出口：** 已找到目标中的真实路径、相关调用约定和可观察消费者；剩余未知项不会被写成既定事实。

### 4. 设计最小且可回滚的改动

1. 优先选择不改变原有分支语义的最小改动，并说明为什么该位置覆盖所需的所有路径。
2. 在目标文件上核实补丁前像、完整指令边界、周边数据、现有引用和实际占用范围。全零或 NOP 区域不能单独证明可安全写入。
3. 对搬迁的数据或表，确认完整索引范围和终止边界；对跳转、调用和循环，证明目标、长度、符号性和边界都符合预期。
4. 若改写返回路径或续接原流程，为桥接逻辑建立清楚、独占的栈帧；逐条推演命中和未命中路径的寄存器、栈和标志位恢复。
5. 保留引擎原有门控和清理逻辑。只有需求明确要求改变它们，且所有受影响路径已追清时才改写。

**出口：** 有目标特定的字节级计划、预期前像、回滚方式和覆盖路径的理由。

### 5. 从单一生成源构建产物

- 让生成器或结构化源码成为补丁字节的唯一事实源；不要让手工补丁文本与生成器各自演化。
- 用程序计算相对位移，并断言目标前像、映像范围、代码块长度、模块边界不重叠、表长度和重要原始字节。
- 以最终生成字节重新计算布局，不能用估算长度占位；完整反汇编每个生成块并检查末字节。
- 写文件前解析并校验所有输出路径；拒绝覆盖目标引擎、输入基线或其他受保护文件，即使调用方显式要求强制覆盖。
- 让应用和回滚都引用同一份补丁定义；在干净的目标副本上确认生成结果可重复。

### 6. 分层验证并定位失败

按本次改动的风险和验收契约记录以下层级，不能用较低层级替代较高层级：

1. **静态检查：** 生成字节、指令边界、跳转目标、前像断言和模块布局正确。
2. **应用/文件读回：** 写入工具执行后，从目标文件重新读取并比对预期字节。
3. **运行时读回：** 在进程中确认目标地址和当前字节正确。
4. **受控启动与路径观察：** 确认目标启动，并观察相关调用、分支、参数和结果消费者。
5. **游戏内验收与回归：** 按契约执行成功、失败、边界和相关原生行为场景。

崩溃时保存现场，先判断失败发生在哪一层，再检查异常地址、调用栈、最近改动和目标边界。用能验证假设的最小调整复现并复测受影响路径。补丁分别通过不代表组合后必然兼容；组合测试聚焦于共享写入、共用调用路径或集成本身改变的行为，并在记录中保留各补丁原有的独立验收证据。

涉及用户手动操作时，一次性列出明确步骤和需要回报的观察结果，暂停等待回复；不要反复轮询或把未发生的操作写成已验证。

### 7. 沉淀可复用知识

完成后记录：行为契约、目标范围、证据层级、准确验收结果、失败与修复原因、回滚位置、尚未解决的问题。把跨项目可复用的方法写进知识库，把目标专属字节和映射明确标成样本线索。

公共材料应只包含经遴选的知识、经验和原创 skill。确有必要时，可引用少量且直接相关的代码或反汇编片段，并注明样本范围；不得发布完整引擎、引擎映像或引擎附带/提取的资产。代码洞清单、项目编号分配、本地路径、内部哈希及私有构建标识应留在项目资料中。公共包使用逐项审核的文件清单，不因文件位于知识库目录就默认获准发布。

## 常见误区

| 误区 | 应采取的做法 |
|---|---|
| 参考引擎里地址和逻辑相同，就直接复制 | 在目标上重新核对函数、调用、表、状态和 ABI |
| 找到一个看起来合适的辅助函数，就把它当必经入口 | 分别证明函数职责、原生路径是否调用它、它是否适合被新逻辑调用 |
| 断点命中或寄存器值符合预期，就认为功能完成 | 继续追到消费点，并完成与需求相符的启动和游戏内验收 |
| 连续零字节或 NOP 就是空闲代码洞 | 检查边界外、数据、交叉引用、运行时用途和最终生成长度 |
| 补丁文本手改正确，就不需要回归生成器 | 从唯一生成源重新构建并验证字节一致 |
| 崩溃地址就是根因 | 先保存现场，结合调用栈、指令边界、改动范围和复现路径定位原因 |
| 一个构建上的样本结论可推广到所有版本 | 说明样本范围，并在每个目标构建上复核关键前像和语义 |
| 改大缓冲区或改表项数量就完成了数据迁移 | 同时追踪初始化/生产端、容量和尺寸描述、索引表以及最终读取范围 |
| 一个陌生的数字消息就是引擎自定义协议 | 先查目标平台的标准消息和 API 常量，再从处理分支确认用途 |
